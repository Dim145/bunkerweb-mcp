# Mapping: linuxserver SWAG to BunkerWeb

Verified at BunkerWeb v1.6.15 for every BunkerWeb name. SWAG names come from `lscr.io/linuxserver/swag` 2.6.0 and its sample files. Per-service settings are `<server_name>_<SETTING>` with `MULTISITE=yes`, or `bunkerweb.<SETTING>` labels with autoconf. SWAG is nginx with certbot and fail2ban around it, so the [`bunkerweb-migrate-nginx`](https://github.com/bunkerity/bunkerweb-skills/tree/main/skills/bunkerweb-migrate-nginx) skill maps the plain nginx directives in more detail. "Run live" means the row was exercised against SWAG 2.6.0 and BunkerWeb 1.6.15; see [verified-live.md](verified-live.md).

## What `proxy.conf` does

SWAG's `proxy.conf` is included in every location. Run live against BunkerWeb with the settings below.

| SWAG `proxy.conf`                                                                              | BunkerWeb                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `proxy_connect_timeout`, `proxy_read_timeout`, `proxy_send_timeout` all `240`                  | `REVERSE_PROXY_CONNECT_TIMEOUT[_n]`, `REVERSE_PROXY_READ_TIMEOUT[_n]`, `REVERSE_PROXY_SEND_TIMEOUT[_n]` set to `240s` on every entry (default `60s`)        |
| `Upgrade` and `Connection $connection_upgrade` on every location                               | `REVERSE_PROXY_WS[_n]=yes` on every entry                                                                                                                   |
| `Host`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`                | sent by default                                                                                                                                             |
| `X-Forwarded-Method`, `-Uri`, `-Port`, `-Ssl`, `X-Original-URL`, `X-Forwarded-Server`          | `REVERSE_PROXY_HEADERS[_n]`: variables work (`X-Forwarded-Uri $request_uri`). Write the port as `443`, not `$server_port`, which is `8443` inside BunkerWeb |
| `proxy_set_header Proxy ""`, `Early-Data $ssl_early_data`                                      | not carried over                                                                                                                                            |
| `proxy_redirect http:// $scheme://`                                                            | no setting; the generated config has no `proxy_redirect`. Check any `Location` header the backend sends                                                     |
| `proxy_cache_bypass $cookie_session`, `proxy_no_cache`, `proxy_next_upstream`, `proxy_buffers` | no setting                                                                                                                                                  |
| (BunkerWeb only) `X-Forwarded-Protocol`                                                        | sent by default; SWAG did not send it                                                                                                                       |

## fail2ban

SWAG enables `nginx-http-auth`, `nginx-badbots`, `nginx-botsearch`, `nginx-deny` and `nginx-unauthorized` in `/config/fail2ban/jail.local` (`ssh` is off). Defaults: `bantime` 600, `findtime` 600, `maxretry` 5 (2 for `nginx-badbots`), `ignoreip` the three private ranges.

| SWAG jail setting                                                                             | BunkerWeb                                                                                                                                                                                        |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `maxretry`, `findtime`, `bantime`                                                             | `BAD_BEHAVIOR_THRESHOLD`, `BAD_BEHAVIOR_COUNT_TIME`, `BAD_BEHAVIOR_BAN_TIME` (defaults `10`, `60`, `86400`). Run live with `5`, `600`, `600`: the ban came on the 5th bad response in block mode |
| `nginx-deny` (`deny` rules), `nginx-unauthorized` (401), `nginx-http-auth`, `nginx-botsearch` | `USE_BAD_BEHAVIOR` with `BAD_BEHAVIOR_STATUS_CODES` (default `400 401 403 404 405 429 444`): one counter per client and service, not one per filter                                              |
| `nginx-badbots`                                                                               | `BLACKLIST_USER_AGENT`, `BLACKLIST_COMMUNITY_LISTS` (default includes `ua:mitchellkrogza-bad-user-agents`). Not run live                                                                         |
| `ignoreip`                                                                                    | no equivalent. `WHITELIST_IP` skips every check for that address, not only bans. Not run live                                                                                                    |
| a custom filter in `/config/fail2ban/filter.d/`                                               | no setting; `BLACKLIST_URI` or a ModSecurity rule is the nearest match                                                                                                                           |
| the ban itself (iptables chain `f2b-<jail>` inside the SWAG container)                        | an nginx-level ban: the next request gets 403 (`is banned with reason bad behavior`). In detect mode the same run banned nothing and logged no counter lines                                     |

## Observed prefix edge cases

The deep path/query, trailing slash, encoded slash, space, UTF-8 and doubled slash matched. The source fixture had `location /echo { return 301 $scheme://$host/echo/; }` beside its stripping `/echo/` location: both bare `/echo` and lookalike `/echox` redirected, and the redirect dropped the query. The initial regex matched neither. A separate **prefix** `REDIRECT_FROM=/echo`, `REDIRECT_TO=https://example.com/echo/`, `REDIRECT_TO_STATUS_CODE=301` matched both redirects on the tested HTTPS service, including `/echo?q=1&r=a%20b`; `/echo/` and deeper paths still used the regex. Use `^/echo$` only if the actual source has an exact bare-path redirect. Check other lookalikes and the served name/scheme before cutover. A fixed target does not establish dynamic scheme or Host parity. `/echo/../admin`, sent with `curl --path-as-is`, left the stripping location: SWAG served its static index (`200`, no upstream), while the prefix-only BunkerWeb fixture proxied the original request line. Carry the static fallback and its access controls separately. In compose, escape every `$` as `$$`. See [verified-live.md](verified-live.md) for the request tables and Lua/CRS proof.
