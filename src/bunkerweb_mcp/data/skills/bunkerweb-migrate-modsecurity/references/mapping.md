# Mapping: ModSecurity to BunkerWeb

Verified at BunkerWeb v1.6.15. For a ModSecurity or OWASP CRS install that sits on nginx or Apache and has its own rule files. BunkerWeb already runs ModSecurity with the CRS (`USE_MODSECURITY=yes`, `USE_MODSECURITY_CRS=yes` by default), so the work is moving **your** rules and settings, not the engine or the CRS. For why a rule works or not once it is in, and for exclusions, use [`bunkerweb-modsecurity-crs-tuning`](https://github.com/bunkerity/bunkerweb-skills/tree/main/skills/bunkerweb-modsecurity-crs-tuning).

BunkerWeb 1.6.15 has no setting for the paranoia level or the anomaly thresholds: both are `setvar` lines in a `modsec-crs` file. Environment variable names in the second table are those of the `owasp/modsecurity-crs` 4.x image; re-check them against the image the user runs.

## Which file goes in which type

The CRS container, and a stock CRS install, load two files around the rule set. They map one to one:

| Source file or directive                                                                        | BunkerWeb type | Verified                                                                                                                                                                |
| ----------------------------------------------------------------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `REQUEST-900-EXCLUSION-RULES-BEFORE-CRS.conf`: `ctl:` exclusions, custom `SecRule`, `SecAction` | `modsec-crs`   | A `ctl:ruleRemoveById` on a phase 1 rule (`920440`) works only from here. A phase 2 target (`ctl:ruleRemoveTargetById=942330;ARGS:q`) works from either type.           |
| `RESPONSE-999-EXCLUSION-RULES-AFTER-CRS.conf`: `SecRuleRemoveById`, `SecRuleUpdateTargetById`   | `modsec`       | Both directives also worked from `modsec-crs` on BunkerWeb. They did **not** work before the CRS on the Apache variant, which is why that file exists: keep them after. |
| Custom rules that must keep running with `USE_MODSECURITY_CRS=no`                               | `modsec`       | These includes load outside the CRS conditional.                                                                                                                        |
| Custom rules that must stop running with `USE_MODSECURITY_CRS=no`                               | `modsec-crs`   | These includes are inside the CRS conditional.                                                                                                                          |

Rule of thumb that held in every run: put each `ctl:` in `modsec-crs`, each runtime exception (`SecRuleRemoveById`, `SecRuleUpdateTargetById`) in `modsec`.

## Moving the files

- In the answer, give each file with its path and its full text, even when it is a copy of a source file.
- One file per concern, name ending in `.conf`. A file without that extension is never included and nothing reports it.
- Docker: a `<SITE>_CUSTOM_CONF_MODSEC_<NAME>` or `<SITE>_CUSTOM_CONF_MODSEC_CRS_<NAME>` variable on the scheduler, or a file under the scheduler's `/data/configs/modsec/` and `/data/configs/modsec-crs/` (per service: a subdirectory named after the first `SERVER_NAME`, `/data/configs/modsec-crs/<server_name>/`). The mounted-directory form was run live. Autoconf: a `bunkerweb.CUSTOM_CONF_MODSEC_<name>` label on the application container. Linux: `/etc/bunkerweb/configs/modsec/`. See the [custom configurations docs](https://docs.bunkerweb.io/latest/advanced/#custom-configurations).
- Renumber any rule whose `id` falls in a range BunkerWeb already emits: `200000` to `200006`, `900200`, `900990`, and `1000` when `USE_WHITELIST=yes`. A duplicate `SecRule` id rejects the whole reload (even `200002`, BunkerWeb's own); a duplicate `SecAction` id such as `900200` loads without a message. The live run used ids from `1000001` up, none of which clashed.
- End every `chain` with a rule that has its own action list (`"t:none"` is enough). A chained last rule with no actions, followed by a comment or another line, fails the reload with `Expecting an action`.
- Delete every directive the engine does not know. `SecServerSignature` fails the reload with `SecServerSignature is not supported`.
